## What the checks observe

Read at `643ae7d5dea236e2b9fc324efd14ec3bdceea2a2` on 2026-11-25. Fisher already requires invariants as property tests: the same statement must hold over many inputs. Whole-workspace mutation runs on pull requests and weekly. It checks whether the current tests notice changed behavior. Region coverage counts which parts of the compiled source the tests execute. Neither supplies an expected answer. [Evidence policy](../evidence.md) · [Workflow](../../.github/workflows/check.yml)

**Rules.** The comparison starts 21 games from the starting position and four from each of five other published positions, always with the same seeds. It compares check, every legal move and the resulting FEN for *each* move. For the next ply, it plays the selected move in shakmaty and constructs fisher's position from that FEN. Fisher's position contains exactly the six fields that FEN prints. A wrong castling right or clock would already appear in the comparison one ply later. Carrying the same six fields forward buys no additional observation today. [Position](../../crates/rules/src/lib.rs) · [Reference games](../../crates/rules/tests/positions.rs)

**Published results.** The bench already checks cumulative node counts through four plies on all six positions each commit. From those roots four plies cannot expose a king stepping beside the other king. Before fisher-j07 widened the fixed reference games, deleting king attacks along a rank or file passed the local check. Only the manual deep run caught it: Position 3 at depth seven gave 178,633,737 against 178,633,661 published. Today's fixed games also catch that break. The approved deep run took 33.46 s and later 35.55 s locally. The ordinary search suite checks ten of 100 published mates. **Search.** The generated comparison checks 36 positions at depth two against material minimax over shakmaty. Other examples reach depth four. An illegal later move already fails independent replay. **UCI.** The threaded test enumerates 11,111 input strings of zero to four steps. One input step can produce several reports. A separate test queues A, `go infinite`, `stop`, B, `go`, `quit`, then sends the two worker reports and checks both forced moves. Repeating a string fixes the inputs. The operating system still chooses when native threads run. Commands and worker events reach one channel and one session loop. [Threaded histories](../../crates/uci/tests/threaded_session.rs) · [Session](../../crates/uci/src/session.rs)

There is already a disagreement about which position owns a response. The history checker accepts four- and five-field FENs followed by `moves e2e4` and accepts a best move for the resulting position. Production sends those fields to a parser that requires six. A generator using the checker as its judge could blame a legal move from the previously accepted position, or approve a move from a rejected position. The owner is tracking the disagreement separately. **Matches.** Acceptance records two manual 1,000-game matches, with normal termination and independent replay. Weekly CI repeats workspace checks without playing this match. ## Where to spend CI time

For each proposed check, a person or agent who will not implement it writes the property, expected answer and deliberate fault first. The owner approves them. The implementer runs the old checks on the broken copy before adding the new check. Require the old checks to pass, the new one to fail for the predicted reason, and the restored code to pass. If the old checks already catch the fault, that example earns no new CI time. Keep the first failure and revision for the owner. The following spending budgets are proposals. Hosted times are unmeasured.

**Weekly fresh seeds.** Targeted generation chooses legal games from selected roots. Reuse today's generator and shakmaty, the independent rules library. Keep the fixed games on each commit. Weekly, start from the published roots with new seeds and compare every legal move and resulting FEN as today. Save revision, root FEN, seed and moves through the first mismatch.

Try a broken en passant check that wrongly rejects a capture when two pawns could capture the same pawn. First establish that the fixed suite misses that particular break. Give the pilot one day and ten release minutes per batch to find and replay it. If it cannot, report that result before scheduling. Maintain the replay alongside the generator. [Shakmaty 0.30.3 README](https://docs.rs/crate/shakmaty/0.30.3/source/README.md)

A disagreement needs adjudication by the chess rules and a third implementation. Both implementations can agree on a wrong FEN clock. Perft and mate results do not specify either clock. Derive the halfmove clock by counting plies since the last capture or pawn move, and increment the fullmove number after Black moves. Have the independent author work a short game by hand and commit the owner-approved six-field FENs before testing the implementation. [Glossary](../../GLOSSARY.md) · [Expected-value policy](../evidence.md)

**Weekly published suite.** Use the owner's `FISHER_PERFT_DEPTHS=6,5,7,5,5,5` and all 100 published mates in release. The local measurements cover perft alone. Give the weekly run its own job because the shared check job has a 15-minute timeout. Use the existing ignored tests and expected data.

For a current sensitivity check, deliberately return the wrong best move on one published root outside the first ten. Require today's ordinary suite to pass and the full run to identify that puzzle. Record all six counts, 100 results and hosted runtime. The earlier deep-only failure is separately documented by fisher-j07. [Acceptance command](../uci-acceptance.md) · [Published data](../../expectations/README.md)

**Weekly match pilot.** After fisher-5sg.10 and fisher-op4, give the pilot one day and one 30-minute hosted slot. Use the acceptance recipe with a pinned runner, release binaries, 1,000 games at 2+0.05, warning log and independent PGN replay. Pass only for 1,000 normal terminations, zero illegal moves, crashes or losses on time, and an empty warning log.

On a throwaway binary, delay a best move past the real clock late in a long game. Require ordinary checks to miss it and the runner to record a loss on time. Keep the first affected game, clocks and runner version. A busy runner can affect timing, so record concurrency and elapsed time. This samples reliability. A strength claim separately needs SPRT, a sequential probability ratio test with bounds agreed before the match. [Match recipe](../uci-acceptance.md) · [Strength evidence](../evidence.md)

## When a new tool would earn its cost

Tool documentation read 2026-11-25. For each deferred pilot, allow one day locally and ten minutes per invocation before considering CI. The independent author supplies the property below and the owner reviews the first counterexample and the assumptions. A run that times out leaves the claim open.

**Property testing with proptest** generates inputs for a statement the owner has approved. Keep doing this as the evidence policy requires. Add the library when a property needs a new generator. Once rules retain repetition history (fisher-3k5), an incremental hash or make/unmake data, carry fisher's position down the game. Compare repetition with an independent move history, a hash with full recomputation, or an unmade position with its saved predecessor. Break one update and retain the failing game. Maintain only the generator for the representation that lands. [Proptest 1.12.0](https://docs.rs/proptest/1.12.0/proptest/) · [Existing invariant examples](../evidence.md)

Defer more than four generated input steps in UCI. First settle the FEN disagreement. If the held-move path changes, start with one deterministic case in which A's report arrives *before* stop, then B starts. The queued-command test delivers A's report *after* stop. Generate variations in readiness and report order only if an independent author shows a fault that survives both the existing suite and that single example. The owner should be able to read the exact history and identify which accepted search owns each response.

**Loom** explores thread orderings through instrumented synchronization, meaning replacements for Rust's thread and lock operations that the test scheduler controls. Today it could vary arrival order at the session channel. The loop already processes those events one at a time. Revisit at fisher-a2q.2 when search workers actually share mutable data. Exercise the real publication path and show the order that lets two workers publish a best move for one search.

Bound preemptions (switches away from a runnable thread), record the bound and keep the substitutions current. Loom does not model elapsed time. **Shuttle** can sample and replay schedules of a larger instrumented test if Loom exceeds the time box. A passing sample leaves unexplored orders. [Loom 0.7.3 documentation](https://github.com/tokio-rs/loom/blob/v0.7.3/src/lib.rs) · [Shuttle 0.9.10](https://docs.rs/shuttle/0.9.10/shuttle/)

**libFuzzer** changes inputs to reach new code. cargo-fuzz runs it on Rust. At fisher-uqk (Lichess play), or a change to the FEN parser, start with a corpus, a saved set of example FENs. Check two claims separately: parsing returns without panic, and fisher agrees on acceptance with an independent parser *on the same input*. First have the independent author specify standard chess, exactly six fields and known differences in accepted notation. A permissive reference must apply that contract. Retain disagreements for adjudication.

The workspace denies panic, unchecked indexing, unwrap and expect. Weakening the field-count check can wrongly accept five fields without a panic. Require that disagreement to be detected. Pin a separate nightly compiler and maintain the corpus and reference policy. Fisher itself pins stable Rust 1.99.1. The owner reads a short input and both decisions. [cargo-fuzz 0.13.2](https://github.com/rust-fuzz/cargo-fuzz/blob/0.13.2/README.md) · [LLVM 23.1.6 libFuzzer guide](https://github.com/llvm/llvm-project/blob/llvmorg-23.1.6/llvm/docs/LibFuzzer.md) · [Workspace lints](../../Cargo.toml) · [Toolchain](../../rust-toolchain.toml)

**Kani** checks Rust assertions over symbolic input, a value that stands for every value admitted by the check. An ordinary loop can test all 64 squares. Revisit if rules adopt bitboards or magic tables, where a lookup depends on a whole pattern of occupied squares. Write a harness, a small entry point calling the production lookup, and compare it with an independently written walk along a rank, file or diagonal. Change one mask and require a specific occupancy with a wrong attack. Pin the verifier and maintain the harness. Review the input assumptions and whether the proof covers every loop iteration. [Kani 0.68.0](https://github.com/model-checking/kani/blob/kani-0.68.0/README.md) · [Safe Rust decision](../adr/0001-rust-with-unsafe-forbidden.md)

**TLA+** describes the ways a system may change. **TLC**, its model checker, explores the states of a finite model. At fisher-2ha, model a pondering search receiving `ponderhit`, `stop` and worker completion in different orders. Specify when a best move may be released from the owner-approved protocol. Allow early release deliberately and require a trace showing the premature response.

Pin Java and TLC, maintain the correspondence between model events and UCI transcripts, and reproduce the trace against Rust. The owner reads the trace. TLC checks the model alone. [TLC guide, tool version 1.7.4](https://docs.tlapl.us/using:tlc:start) · [TLC release](https://github.com/tlaplus/tlaplus/releases/tag/v1.7.4)

**Lean** checks proofs of precisely stated theorems. Alpha-beta already has a published correctness proof. Fisher's question is whether its Rust search implements it. A separate Lean proof would require an independent theorem statement, owner review, a maintained mapping to Rust and proof checking in CI. The planned comparison tests the implementation directly. No Lean pilot or CI allocation for fisher-4yn. [Lean 4.36.0 language reference](https://lean-lang.org/doc/reference/4.36.0/) · [Knuth and Moore, 1975](https://www.sciencedirect.com/science/article/pii/0004370275900193)

**Fault injection** makes a dependency fail on demand. When an I/O boundary changes, use a failing writer, disconnected reader or failing thread factory to check the caller's promised outcome. When a constructor or input assumption changes, revisit the previously unreachable branch. These small tests charge CI for a specific failure that ordinary legal games cannot produce.
